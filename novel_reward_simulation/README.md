# Novel Reward Function Simulation

This folder implements our proposed extension to the iRDRC MDP's reward
function, as introduced on the "Proposed Direction" and "Architecture
Explained" slides of `review 1/presentation/review1_presentation.pdf`. It
keeps the base paper's state space, action space, and transition model
exactly as they are — only the reward function `R` is extended, so this is a
same-tuple, updated-`R` variant of the base paper's MDP, not a redesign of it.

## What's new here vs. the base paper

The base paper's reward has five cases, built around four fixed weights
(`r1, r2, r3, r4`), and treats radar purely as a hazard detector:

```
r_t =  +r1   if a=comm, good channel, no event
       +r2   if a=comm, bad channel,  no event
       -r3   if a=comm, event occurs        (dominant penalty)
       +r4*(b+1)  if a=radar, event occurs
        0    if a=radar, no event
```

Our proposal adds two more terms on top of that, without touching the
original four:

- **Dual-role radar (`r5`):** in the base paper, a radar scan that finds no
  hazard gets zero reward — the information is thrown away. Here we track a
  scalar belief-uncertainty `u ∈ [0,1]` that grows every step the vehicle
  doesn't sense, and gets pulled down whenever radar is used, hazard or not.
  The radar action earns `+r5 * (u - u_next)`, rewarding it for actually
  reducing uncertainty, not just for catching hazards.
- **Priority- and deadline-aware penalty (`r6`):** the base paper treats every
  packet in the queue as interchangeable. Here the head-of-queue packet
  carries a priority level and a deadline countdown; if it expires unserved,
  the step is penalized `-r6 * priority`, scaled by how urgent the dropped
  packet was.

`r3` (the hazard-miss penalty) is left untouched and still dominates both new
terms by construction, so "safety first" from the base paper still holds —
the novelty adds new things to optimize for, it doesn't dilute the old one.

## Files

```
params.m                   base paper's constants + the new r5/r6/uncertainty/
                            deadline parameters
state_space.m               same 352-state space as the base paper
event_probability.m         base paper's marginal P(⊕) formula (eq. 1), kept
                            for the state-space/sanity check in main_demo.m
state_event_probability.m   state-conditional P(⊕), used inside step_environment.m
                            so the event probability actually depends on the
                            current risk state instead of being a constant
novel_reward_function.m     the extended reward: base 5 cases + r5 (dual-role
                            radar) + r6 (deadline/priority penalty)
step_environment.m          one environment step: advances the queue, channel,
                            risk factors, belief uncertainty, and packet
                            deadline, then scores it with novel_reward_function.m
discounted_return.m         same discounted-return helper as review 1/simulation

main_demo.m                 sanity-checks state space size + P(⊕), then runs
                            round-robin / always-comm / always-radar under the
                            novel reward and reports reward, queue length,
                            uncertainty, and deadline misses per policy

base_params.m               unmodified copy of the base paper's params, kept
base_reward_function.m      local so this folder is self-contained and the
base_step_environment.m     A/B comparison below doesn't depend on review 1/

compare_with_base.m         runs all three baseline policies under both the
                            base paper's reward and the novel reward, on
                            matched seeds, and writes every chart + the
                            summary table into results/

results/                    generated by compare_with_base.m — see below
```

## The comparison in `results/`

`compare_with_base.m` runs round-robin, always-comm, and always-radar under
the base paper's reward and under the novel reward on identical random seeds,
so the only thing that differs between the two runs is the reward function
itself.

```
results/compare_discounted_return.jpeg     G(pi): base reward vs. novel reward, per policy
results/compare_total_reward.jpeg          total reward: base vs. novel, per policy
results/novel_deadline_misses.jpeg         deadline misses per policy (novel reward only —
                                            the base paper has no deadline concept at all)
results/novel_uncertainty.jpeg             mean belief uncertainty per policy (novel reward
                                            only — the base paper has no belief state)
results/novelty_comparison_summary.jpeg    all four of the above as one 2x2 figure
results/comparison_summary.txt             the raw numbers behind every chart
```

What it shows: under the base reward, always-radar is the best-scoring naive
policy and round-robin is negative. Under the novel reward, round-robin's
score flips positive (it now gets credited for the uncertainty it resolves by
sensing regularly), and always-radar's score drops sharply once its habit of
starving the queue starts costing it 83/500 deadline misses. Round-robin and
always-comm still show zero deadline misses — because they still leave the
queue open often enough to serve the head-of-queue packet before its deadline
expires — which is exactly the throughput/uncertainty/urgency trade-off a
learned policy (Phase 3) needs to resolve, rather than something any fixed
policy can satisfy by construction.

## Running it

Plain MATLAB, no toolboxes required:

```
cd novel_reward_simulation
main_demo            % environment sanity check + baseline table under the novel reward
compare_with_base    % regenerates everything in results/
```

## Where this sits in the project

This is exploratory groundwork for **Phase 3** (see the main repo README) —
it proves the extended reward function is implementable and behaves sensibly
against the three naive baselines, ahead of building the actual belief-state
estimator and hierarchical mode-selection/packet-scheduling controllers that
Phase 3 calls for.
